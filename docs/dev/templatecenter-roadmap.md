## 11. 后续扩展的改造点

这些本次不做，但设计要能接上。改造范围和顺序在提案 11。

### 11.1 接对象存储（S3 / COS）

**注意这件事和多副本的关系**：如果一上来就要多副本，对象存储（或 RWX）就不是"后续"而是**前置条件**（9.7）。这里只讲对象存储实现本身的改造点。

逐环节改造点：

| 环节 | 本地磁盘 | 对象存储 |
|---|---|---|
| 产物落地 | `BuildExt4` 直接写最终路径 | 写本地临时文件 → `Upload` → 删临时文件；`Ext4Path` 语义从"文件路径"变成"object key" |
| 分发注解里的 URL | 用 `MasterNodeIP` 拼 | 换成预签名 URL |
| Cubelet 拉取 | HTTP 从 template center 拉 | 直连对象存储 |
| 完整性校验 | template center 算 sha256，Cubelet 边下边校验 | 不变 |
| GC 物理删除 | 删本地文件 | 加一步 `ArtifactStore.Delete` |
| template center 数据面流量 | 产物字节都过 template center | **完全不过 template center**（客户端直连对象存储） |

最后一行是接对象存储的一个额外收益：多副本下产物下载流量本来要分摊到各副本（9.8），换成预签名 URL 之后这个端点退化成一次重定向，template center 彻底不碰数据面。

**三个必须处理的坑：**

**① Cubelet 的 host 重写会破坏预签名 URL。** 5.2 那个 `rewriteDownloadHost` 是**无条件**覆盖 host 的，而预签名的签名覆盖 host，一改就 403。解法是在分发注解里加一个标记（比如 `url_kind=presigned`）让 Cubelet 跳过重写。

**这个 Cubelet 改动必须先于存储切换发布**，否则新老版本混跑时会有节点拉不下来。这是个发布顺序约束，容易踩。

**② 预签名 URL 的过期时间要匹配下载耗时。** 产物几个 G，慢节点或跨地域可能要几分钟。过期太短会中途 403，太长又有泄漏风险。建议 30 分钟量级，同时给 Cubelet 加"过期时向 template center 申请新 URL"的重试路径，而不是直接失败。

**③ 顺手能做断点续传。** 现在拉取失败是整份重下。对象存储支持 Range 请求，记录已下载字节加增量 hash 就能续传，对大产物和不稳定网络收益明显。

**安全要求**：ak/sk 必须走环境变量或 Secret 注入，不能写进配置文件或代码；预签名 URL 只签 GET 且限定单个 object key；bucket 不开公网匿名读。

### 11.2 合并快照

数据层面已经隔离好了（按 `kind` 分行），共享库的设计也是为这个铺的。届时把快照的调用方从 CubeMaster 换成 template center 即可。

**真正的难点只有一个：快照的运行时引用计数事件不能丢。**

现在沙箱创建/销毁时通过进程内钩子增减快照的引用计数，判断快照能不能回收。钩子和沙箱状态机同进程，调用同步不丢。快照迁到 template center 后就变成跨进程事件：

- 丢事件导致计数偏高 → 快照永不回收，存储泄漏
- 丢事件导致计数偏低 → 在用快照被误删，数据损坏

解法是三层保障：

1. **至少一次投递**：本地队列 + 指数退避重试
2. **幂等**：按 `event_id` 去重
3. **定期对账**：从 CubeMaster 拉沙箱全量校准计数

第 3 条是兜底，前两条都失效时靠它收敛。

### 11.3 多架构

现在是隐式同构假设。要支持混合架构集群，至少三处要改：

| 位置 | 现状 | 要改成 |
|---|---|---|
| 构建平台 | `defaultPlatform()` 取构建机 `runtime.GOARCH`，请求方指定不了 | 请求可指定 arch，构建时校验构建机能否胜任 |
| 产物身份 | 哈希输入里没有 arch 字段 | 加显式 arch 字段（**会触发一次全量重建**，需评估） |
| 分发选点 | 只按 `instanceType` 过滤 | 加 arch 过滤 |

**docker 导出路径要优先实测**：它取 `RepoDigests[0]`，而 Docker 对多架构镜像的 `RepoDigests` 通常记录 index digest（跟架构无关），那么不同架构构建会算出**相同的 artifact_id**。如果实测确认，这是正确性缺陷不是优化项。

**多副本让这一条变得更要紧**：多副本可以调度到不同架构的机器上，那么"构建平台取构建机自己的架构"就从"确定的单一架构"变成"取决于请求落到哪个副本"——同一个模板两次构建可能得到不同架构的产物，而 `artifact_id` 相同。

所以多副本部署时**必须约束所有 template center 副本同架构**（用 nodeSelector 或 nodeAffinity 固定），直到上面三处改完。这一条要写进部署文档。

e2b 的官方架构文档完全没提 CPU 架构，这块没有现成做法可参考。
